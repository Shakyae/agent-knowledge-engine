# DSH 项目级工程知识自进化：补充研究与架构评审

> 状态：调研与设计建议；未实施、未执行实验。调研基于本机安装版 0.2.2-rc.1 的发布构建与文档，以及另行标明版本差异的官方在线资料。研究目录位于当前工作区 /Users/shakya/dev/dsh-lab；此目录本身不是 Git 仓库，其下 projects/team-demo 是独立 Git 仓库。项目知识应最终属于各自项目仓库，而不是本研究目录。

## 执行摘要

推荐**先采用现有项目约定 + 简短 AGENTS 入口 + 按需 Skill/Markdown + Git，默认人工批准正式发布**，不引入知识数据库、后台服务或插件。在必须检索的任务里，由实际执行者自己检索四类知识；发现可复用经验时就地记录候选；满足条件时交由没有参与生成的合格成员复核；同一批次由一人发布。普通任务可跳过候选提炼，明显无关的小任务可跳过专项检索。分散检索及复用效果仍须实验，不能宣称已经保证。

这条路线适合先验证“后来任务是否主动找到并正确应用”，成本较小；但 Prompt/Skill 是**软约束**，共享 workspace-write 并不防止作者直接写正式库，单靠角色约定无法提供强制审批或可靠自动发布。第二阶段若检索漏项或并发冲突在实验中有证据，可加小型只读检索及校验脚本；只有业务确需可强制、不可绕过的门禁且投入合理时，再评估插件/外部受控发布边界。独立模型审核降低部分遗漏，不证明正确或独立于共同偏差。

**资料边界**：已补读用户指定的 [旧报告](<REPORT-knowledge-ops-v1.0.md>)，差异见下文。此前按 `REPORT-knowledge-ops.md` 精确文件名搜索，遗漏了带版本号的文件；这不是旧报告不存在的证据。旧报告描述的 Windows 环境和 GitHub tree 与本轮 macOS 安装环境不同，不能直接将其运行时配置当成本机事实。本机 DSH 是安装产物，引用可读的编译 JS 与随包 README，不冒充 TypeScript 源码；本轮引用的在线官方 master 文档未固定 commit、未验证与安装版对应。所有效果、成本、可用性和自动发布的安全性均未实测。

## 二、知识存储与检索

每个 Git 项目保有自己的 Markdown 权威知识，优先沿用已有目录和四类格式，不为小项目预建空目录或复制官方全部框架。AGENTS 仅描述简短触发条件、目录入口、内容不可信的边界和人工审批要求；可选 Skill 定义按需执行的检索/提炼流程。知识正文不常驻上下文，权威事实只保留一处，以链接表达关联。是否需要具体索引文件或统一目录留待项目既有约定决定；不可把本报告路径当作任何项目的知识库。

**检索触发**：涉及代码实现、架构决策、排障、部署或风险变更时，执行者在其首次关键行动之前，以受影响模块、技术、错误症状及操作类型为关键词；四类均纳入检索范围，但先看索引/标题，按需读最相关原文，不逐篇全量载入。纯问候、纯格式调整且无行为影响等明显无关任务允许跳过；涉及不确定范围时保守检索。检索条件、条数、文本量采用项目基于实验选定的预算，不预设未测数字。结果多时优先路径、组件、版本和故障症状匹配，读少量高价值条目后扩展；不可为节约预算忽略安全或直接相关规则。

**检索路径**：glob 找文件/隐藏目录，再在明确目录或候选文件内搜索词及同义词，读取原文及上下文；必要时搜索 Git 历史或会话事件核对证据来源。glob/grep 有不同覆盖、截断和权限限制，必要时分目录重查；检索失败记录“未知/未覆盖”，不要报告“没有知识”。每个相关执行者自行进行此流程，Lead 只传目标、边界及重要线索，不替所有成员检索。若成员没有搜索或读取能力，明确向 Lead 求助或人工处理，不能默称完成。

**适用性**：读取状态、范围、创建/复核时间、代码/依赖版本及证据链接，与当前代码、配置、测试或事故上下文核对；过期、已替代、归档或证据不可访问的知识只作为线索，不自动作为当前规范。存在冲突时回到当前实现和权威来源，由负责人决策；仓库内容、外部日志或历史是数据，不允许其自升格为系统指令。任务结果简述适用知识与验证结果，涉及重要无匹配则注明搜索范围；无需每个简单任务都产生知识报告。

## 三、沉淀、审核、发布

**生成条件**：出现可复现且可迁移的决策及其取舍 → Agent Note；重复风险及预防条件 → Defensive Pattern；可靠可重复操作 → Cookbook；有显著影响且可证据化的事故和根因 → Postmortem。个人偏好、一次性细节、未经验证猜测或已有内容的重述一般跳过。证据不够的只作候选/待核实，不提升为事实。记录适用范围、现象或决策、来源/证据、验证方法与结果、限制、关联和作者；敏感信息脱敏，禁止把秘密、个人数据或无授权日志写入 Git。

先搜索正式库及可见候选，按语义和适用范围判断新增、补充、冲突或重复；不以文件名、单一向量阈值判定重复。检索不完整则不自动断言唯一。更新已有事实优先原权威位置；明确替代关系和历史链接，Agent Notes 遵守自身 proposed/implemented/rejected/archived 与冻结约束，其他类型使用项目已有维护规则。归档、删除或破坏性改写不能隐含获授权。提交前复核链接和版本。

候选治理可使用 `草稿 → 提交 → 审核 → 授权 → 发布`，退回、拒绝、失效为分支；这只是建议，不是 DSH 内置状态机，也不替代四类文档自身生命周期。候选应绑定作者/参与者、内容版本或 hash、目标旧版本、事实来源、去重结果与验证。审核者独立于生成过程，核查证据、适用范围、安全、分类、重复及反例；审查结论绑定具体版本，内容/目标变更后失效。**自动生成候选、自动审核、自动发布是三个独立能力**，前两者不授权第三者。

Single Session：当前 Session 检索、提炼并提出变更，建议由未参与候选生成且具备领域能力的人类实质审核，并在正式发布（含更新、归档、删除）前明确批准；无合格审核者或未获批准时保留候选，不发布。Team：优先用实际现有成员，但没有符合独立性且可用的成员时人工审核；是否可自动发布不仅需独立审核，还需明确政策、可信身份、权限隔离和执行门禁。默认仍人工授权。成员不可用/被中断或审查未完成即保留候选或跳过，不得静默放行。失败不应影响业务任务本身，除非项目已有强制安全要求。

单一发布者由 Lead 在批次开始指定（可为 Lead 或合格成员）；候选作者通过消息/任务提交，不同时写正式文件。发布者确认版本、去重及授权，串行整合 diff；发现目标或候选变更时停下并重新审核。发布前检查工作区和未提交变更，只处理指定文件，不覆盖用户工作；Git 以可审阅提交保留追溯。发布失败/中断记录未完成状态，核对实际提交再恢复；回滚通过受授权的 Git revert 或经审查的反向变更，不使用破坏性 reset 覆盖他人工作。上述为协作约定，无法阻止绕行的外部写入。

### 自动发布的必要前提（非当前能力承诺）

仅对低风险、可验证、无秘密、无权限/安全策略或既有知识删除变更的预先批准范围考虑自动发布；高风险、事实冲突、证据不足、跨文档大改均人工。政策明确审核资质、可发布类别和操作，可信不同主体独立审核不可变候选并绑定 hash、目标旧版本、政策版本和证据，发布端重验去重、权限与条件；失败、冲突、缺失或不可观测一律 fail closed。候选者与审核者不能绕过发布端写正式库，所有文件、shell、Git、插件及外部入口均须纳入权限边界。仅共享工作区和提示词不满足此条件。多文件变更需受控提交、可恢复状态及幂等处理；Git 本身不自动保障授权或阻止直接写入。此程度可能需要外部保护或新组件，必须单独设计、评估成本并获用户授权。

## 四、动态职责映射与四原则评价

**Preset 核查事实**：本机安装插件为 0.1.9，和 DSH 0.2.2-rc.1 的证据及构建文件路径见 [Team 专题](<findings/02-team-presets.md#L11-L16>)。本会话的工具与活跃 Team preset 声明表明存在 Team 模式，`list_agents` 可观察实际 roster/状态；更一般地，工具 marker 缺失不能反证不存在 Team，执行摘要也不能证明成员读过什么或具备某项能力（[观测限制](<findings/02-team-presets.md#L18-L32>)）。角色是模板不是实例，成员的 persona 包含其角色及 Team 分工，并不继承其他成员完整 prompt；fresh 不带队长历史，fork 带已完成轮次，派单须自包含。角色、路由与策略在创建时持久化，Team Skill 按角色注册于 Agent scope 而非全局；工具实际能力取决于当前可达能力与 slot policy，目录并集不等于真实可用工具。上述为插件实现而非跨版本保证，详细源码位置见 [传递机制](<findings/02-team-presets.md#L34-L55>)。运行态状态、实际工具和技能需核对，角色描述不能证明资格。runtime/store 或已绑定 skill 发布失败等情形会拒绝创建，quarantine 下可用工具受限（[故障表](<findings/02-team-presets.md#L64-L76>)）；它们不等于知识审核或发布门禁。

按每个任务实际需要的可用成员能力而非名字映射：执行者能查找/读取并理解所属子任务；提出者有一手证据；审核者能独立验证且没有参与该候选生成，具备必要领域和读取能力；发布者具备受授权写入与冲突处理能力。一个人可以承担多个不冲突职责，但提出者不得审核自己的候选；模型不同、成员不同或 fork 不自动证明独立。Lead 对适用范围、冲突与退化负责，不是所有检索的串行代理。

| 模式 | 具体分配 | 退化 |
|---|---|---|
| Single | 当前 Session 检索与提候选；人类批准正式发布 | 无能力检索则说明未知；未批准不发布 |
| 双人（Lead + 1） | 两人各自执行前检索；一人提候选，另一人若没参与生成且有能力则审核；一人负责发布 | 双方均参与生成、审核者不可用或资格不明时人工；不为了知识事项必定召唤第三人 |
| 多人 | 相关执行者分散检索、就地提候选；未参与生成的合格成员审核；单发布者合并 | 审核者不可用、独立性无法证明或多人同时改写时暂停该候选并转人工/重审 |

四原则在逻辑上相容，能降低中心瓶颈与冲突，**但源码静态核查不能证明实际检索触发、正确使用、成员独立及单发布者排他性**。独立性需判断上下文、共同输入、共享生成与真实审查证据；独立模型也有同源偏差，尤其错误前提会被共同接受。共享磁盘里“唯一发布者”只有合作约定，不能等同安全锁。验证设计见 [实验计划](<experiments/validation-plan.md>)。

## 五、方案比较及裁决

| 路线 | 复杂度与维护 | 可靠性 | Token/流程影响 | 跨平台与适用前提 |
|---|---|---|---|---|
| 1. AGENTS + Skills + Markdown + Git | 最低；复用项目约定，维护入口及内容 | 软约束；人工审核；不保证触发或防绕过 | 按需检索，少量额外调用；成本待测 | Markdown/Git 可移植；具体 DSH 插件/权限与搜索差异需确认 |
| 2. 路线 1 + 少量检索/校验脚本 | 中等；需要维护脚本、测试与运行环境 | 可检查格式、链接、索引、版本及调用记录，不能证明理解、独立或权限不可绕过 | 减少重复搜索或增加进程开销均待测；按需运行 | 脚本语言、shell、编码和文件路径需跨平台设计；不是必备前置 |
| 3. 专门插件或生命周期钩子 | 高；接口、升级、权限、故障及持续兼容成本 | 可能在受控入口检查，但若存在旁路或钩子未覆盖则仍不强制；本轮未证实钩子满足需求 | 可能减少提示重复，也会增加每任务开销和故障影响；待测 | 绑定宿主及版本，部署与维护最重；不天然更先进 |

**裁决**：从路线 1 开始并默认人工发布；同时以独立盲测验证复用与成本。只有数据表明检索覆盖、结构检查或冲突处理成为瓶颈时考虑路线 2；只有明确需要可靠强制边界且能投入隔离与运维时才评估路线 3。方案是建议而非授权实施；脚本/插件皆不能仅靠存在就保证执行效果。

## 七、主要风险、未验证问题与下一步

- **上下文与检索**：指令可能截断、上下文压缩、搜索结果不全、技能被遮蔽或未加载；预算、触发率及跨任务正确复用须在新会话盲测，知识不是天然被主动发现。
- **独立性及共同错误**：资格与实际参与情况需核验，双代理不等于独立事实来源；缺失即人工。形式审核不可替代可复现证据。
- **权限与并发**：同可写工作区的角色隔离并非安全隔离；单文件 CAS 非多文件事务；外部写入、变更后复用审核及失败恢复均需验证。
- **成本与干扰**：对简单任务允许跳过专项检索及候选提炼；不能把“不显著增加成本”写作已验证结论。实验记录耗时、token、调用、错误应用和开发任务结果，与无知识机制对照。
- **资料版本**：旧报告基于另一个运行环境及所列 tree，本机安装包与在线 master 并未证明逐项一致；旧报告引用的脚本及钩子行为未在本轮重新实跑或全面核验。

[最小验证实验计划](<experiments/validation-plan.md>)覆盖 Single、双人、多成员和对照退化、跨任务盲测与安全门；目前仅设计，未执行。核心验收是实际找到、判断适用、正确改变行为并验证结果，而不是文件存在。

## 八、真正需要用户决定的事项

1. 在看到实验设计后，是否授权后续于隔离测试仓库进行实验及必要的模型调用？本轮未执行。
2. 若未来确需无人工自动发布，需先决定允许自动发布的具体低风险范围、可信审批/身份与权限隔离的投入；此前保持人工批准。其他目录命名和局部字段可依据各项目既有规范由实施者决定。
