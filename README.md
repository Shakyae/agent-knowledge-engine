# Agent Knowledge Engine (AKE) v0.4.0

A portable, low-intrusion engineering-knowledge layer for coding agents. Agents retrieve existing project knowledge when relevant, capture reusable results in one of four knowledge kinds, and publish through a bound review/authorization gate. The AKE Skill workflow requires an eligible independent reviewer and explicit user authorization before publication; author self-review is recorded honestly but does not substitute for that review. The CLI retains its automatic authorization mode for compatibility, but the Skill does not use it as a default.

There is no server, database or plugin: knowledge is Markdown in the project's Git repository, behaviour is described by a Skill plus `AGENTS.md`, and a dependency-free Node CLI performs the format checks, keyword retrieval, candidate lifecycle and publish gate.

**Naming:** AKE = **A**gent **K**nowledge **E**ngine, and the CLI command is `ake` (the project abbreviation). The earlier working name `PKO` (project-knowledge-ops) and the CLI name `kno` were retired before v0.1 was delivered; the rename is recorded in `.agents/notes/implemented/process/2026-11-10-rename-working-name-to-ake.md`.

## What it solves

Agents start every task in a new context. Durable, project-specific knowledge — why a design is what it is, which defect classes keep reappearing, what actually happened during an incident, which procedure was verified — otherwise has to be rediscovered or is lost.

AKE gives that knowledge:

- **a place**: four knowledge kinds adapted from the official DSH conventions,
- **a way in**: `ake search` plus a Skill that defines when and how to search,
- **a way to grow**: candidates captured where the experience emerged, with evidence and applicability recorded,
- **a way to stay honest**: explicit review/authorization modes, a hash-bound publish gate and audit records,
- **an honest boundary**: it is a process and tooling layer, not a security mechanism (see [Limitations](#limitations)).

## Requirements

- Node.js >= 22.20.0 for AKE itself (no third-party runtime dependencies); AKE leaves the target project's own Node version declaration unchanged.
- Git (initialization refuses to run outside a valid Git work tree).

## Use AKE in a project (v0.4.0)

### Install the Skill and initialize projects

The AKE host (repository CLI and distributed Skill helpers/shared CLI) requires Node.js >= 22.20.0; entrypoints fail before task dispatch when run on an older host. This does not change the target application's own Node declaration, and AKE initialization leaves its package metadata untouched. The Skill's preflight executes only the shared CLI bundled with the Skill against the target config; it never executes or upgrades `.ake/tools` legacy copies. Bootstrap preserves existing project config and never installs project-local CLI files. A real `ake update` run acquires the pinned Vercel Skills CLI `skills@1.8.1`, whose package declares Node.js >= 22.20.0; `ake update --dry-run` and an up-to-date result do not acquire or execute it. An attempted native Windows Node.js 20 run failed when Skills CLI 1.8.1 used `fs/promises.glob`; the Windows W1-W4 update-acceptance workflow passed on Node.js v24.22.2. Node 24.22.2 is the tested Windows workflow runtime, not a higher AKE minimum. The third-party `npx skills add` installer is outside AKE's runtime gate; follow that CLI's own Node requirement. Install the Skill from the official GitHub repository at a pinned full commit SHA (review and back up existing installations first):

```bash
npx skills add Shakyae/agent-knowledge-engine@<full-commit-sha> --skill ake -g
```

Initialize knowledge layout separately through the loaded Skill. Resolve its base directory from the Skill loader; do not substitute the AKE source checkout for target-project operations. For a target without `.ake/config.json`, preview and then apply the bundled bootstrap. For a target with a regular `.ake/config.json`, run preflight once instead:

```bash
node /absolute/path/to/ake-skill/bootstrap.mjs --dir /absolute/path/to/project --dry-run
node /absolute/path/to/ake-skill/bootstrap.mjs --dir /absolute/path/to/project
node /absolute/path/to/ake-skill/preflight.mjs --dir /absolute/path/to/initialized-project
```

Installation adds the agent Skill; initialization creates project knowledge directories and `.ake/config.json`, but does not copy a project-local CLI. The supported execution path is the shared CLI shipped at `<Skill base>/resources/ake-source/scripts/ake.mjs`; pass `--project <absolute-project-path>` to select a project explicitly. `.ake/tools/` files from earlier installations are legacy copies: they are ignored, left byte-for-byte untouched, and must not be executed or overwritten. External scripts that previously invoked `.ake/tools/scripts/ake.mjs` must migrate to the shared Skill CLI and pass `--project`; remove old copies only after an operator has reviewed them. Skill installation and project initialization remain separate. Initialization does not install or inspect Skills, and Skill presence does not prove it was loaded. Each project's data stays in that project. Without `--project`, the CLI searches from the current directory to the nearest Git root and uses the nearest ancestor with a complete valid `.ake/config.json`, supporting an AKE subproject inside a larger repository. A broken or unsafe inner `.ake` stops resolution instead of falling through to a parent AKE project. Explicit `--project <dir>` always uses that exact directory (and its own defaults when no config exists, including an empty `.ake/` created by earlier writes). Effective paths are validated after defaults are merged, so inherited or custom paths through an escaping symlink are rejected even with partial or missing config. `init` leaves differing existing files untouched and reports conflicts; it may still create other safe items. An existing unmarked `AGENTS.md` gets the current marked trigger block appended by default, preserving all original bytes and remaining idempotent. A prior AKE-managed block with older/different rules is not automatically upgraded: it is reported as a conflict and left untouched. Back it up and manually review/merge the new rules; AKE never silently overwrites an existing block. Malformed marker blocks also remain conflicts and are never overwritten. `--merge-agents` is retained as a compatibility flag.

The distributed `skills/ake/` bundle also contains `bootstrap.mjs`, `preflight.mjs`, the separate `init-git.mjs` helper and the shared CLI with its modules, templates and minimal package metadata. After installing this Skill, initialize and operate on projects without an AKE source checkout: use the absolute Skill base directory supplied by the Skill loader, the bundled `bootstrap.mjs`/`preflight.mjs` entry appropriate to project state, and the shared CLI with an absolute target path. For an initialized project, `preflight.mjs` executes `status --json` through the Skill-bundled shared CLI, not a project-local CLI; success verifies project selection only, not task-command compatibility. It does not authenticate the CLI's identity or guarantee absence of side effects. The shared Skill updater remains the supported route for updating that Skill bundle; do not update each project separately. The target may be a Git work-tree root or a project subdirectory in an existing parent work tree; neither requires a first commit, and an existing parent work tree must not get a nested `.git`. Bootstrap and its dry-run never run `git init`. Only a stable `NOT_GIT_WORKTREE` from bootstrap, or the same stable result from preflight corroborated by its exact controlled status diagnostic and independent trusted Git inspection, is eligible for the Skill's consent flow; all other failures stop without a prompt. The Skill first inspects the exact target read-only and displays its canonical path. In a Team, only the Lead asks the user and runs `init-git.mjs`; before displaying the choice, the Lead freshly inspects the target and uses that inspection identity to display the exact canonical path. After the user selects initialization for that same path, the Lead directly invokes the helper using the same pre-choice canonical path and identity; the helper rechecks identity and Git state and stops on mismatch. A child Agent neither asks the user nor runs the helper. Use a host-native choice when available; if the host lacks native-choice capability (not when policy/permissions explicitly deny interaction), the Lead shows the exact path and text options `1 — initialize this target and continue` / `2 — do not initialize yet`. Only an explicit choice to initialize the displayed canonical path authorizes continuation. Only the user's explicit reply `1` to that path-specific prompt authorizes the Lead to execute the helper in the text fallback; native-choice authorization requires the user's explicit initialize choice for that same path. Refusal, skip, missing/ambiguous replies, or any other response do not authorize Git init and end that branch; choosing another target requires a fresh inspection and a new path-specific choice. The workflow ensures consent and execution are not relayed to a child Agent. A child Agent neither asks the user nor runs the helper. Helper parameters are not authorization. The flow requires a single writer and cannot remove Git's residual check-to-use race. If a helper/Git operation exits nonzero, is signal-terminated, fails post-checks, or has an uncertain result, preserve the live state and stop without retry, cleanup, apply, or further AKE writes; report for manual inspection. An explicit policy or permission denial of user interaction is not a trigger for text fallback. The helper returns an inspection-time device/inode/birthtime identity; the write call must pass it back and recheck it before Git operations. This identity binds a directory instance but is not authorization. The Skill offers explicit initialize/skip/choose-another/cancel options: refusal or skip is terminal for Git initialization for that task, and choosing another target requires a new inspection and a new choice through the same native-or-Lead-text flow for that path. It rechecks parent metadata, verifies exact root and expected unborn HEAD, and refuses detected reinitialization output; Git `init` has no atomic create-only mode, so the workflow requires a single writer and cannot eliminate an external race after the final check. Git may also create default configuration and copy templates; no Git-init-only write-set guarantee is made. Afterward the Skill repeats bootstrap dry-run; any conflict stops before apply. For an existing AKE project whose `preflight` status returns stable `NOT_GIT_WORKTREE`, use this same option flow and rerun preflight after success; `GIT_UNAVAILABLE`, bare or generic status failures must not trigger the prompt. The direct AKE CLI itself never creates a Git repository. Bootstrap cleans `GIT_*` environment overrides before verifying Git and fails closed for missing Git, bare repositories, permission/path errors and unrecognized Git errors; existing partial or non-file project state is not treated as a fresh project. If both `.ake/config.json` and `.ake/tools/scripts/ake.mjs` already exist, bootstrap preserves them and does not repeat or upgrade initialization. It compares config version with bundled metadata without executing the project CLI; this cannot prove the CLI version. For an already initialized target, the Agent runs `node <absolute-skill-directory>/preflight.mjs --dir <absolute-target>` once; do not ask the user to run it. This helper only executes `status --json` with cwd fixed to the target realpath, then verifies the returned absolute `project` realpath. Status confirms project selection only, never task-command capability. The Agent then runs the actual task command directly in the same cwd/env. For read-only search, run the intended query/options once and use its original full result, including query, searched roots, coverage, coverage reasons, truncation and results; do not repeat a search via the helper. For writes, do not run destructive probes or block on exact help-text matching: consult available help when useful, then use the actual command and report any incompatibility honestly; ask the user only when the error cannot be resolved safely. Keep cwd/env and target state fixed from preflight through the actual operation; rerun only the status identity check if cwd, environment, project config/CLI or task context changes. Do not rescan before every write in an unchanged context. Reject relative/mismatched/unresolvable `project` values and stop if required capability is absent or cannot be evidenced. Bootstrap `--dry-run` remains distinct and never executes an existing project CLI; zero-project-write claims apply only to bootstrap preview/refusal, not preflight. Preflight executes existing project code, so it cannot guarantee no side effects or authenticate its identity. If host/system policy refuses the helper or child, stop; do not route around through wrappers, MCP or another executor. If the target is wrong, back it up and manually review migration/update guidance against the official AKE source; never auto-copy, upgrade or overwrite existing project files. This is project-local and never installs a global Skill. Missing offline bundle files are reported by exact path; restore/update the Skill from an official AKE source checkout using the installation instructions above. Preview/apply is not atomic or TOCTOU-safe: a concurrent writer can change files between them, and the core initializer may then produce mixed outcomes. Use a single writer; the zero-write conflict guarantee applies only when the preview detects a conflict, not concurrent changes after preview. The prompt-level requirement to ask before proceeding when the selected target is not a Git project is a soft Skill instruction; script tests establish refusal/zero writes, not real agent questioning or compliance.

Skills CLI 1.7.6 was tested on macOS with a temporary HOME and project: for the commands above it created a real canonical `.agents/skills/ake` directory and a Claude Code `.claude/skills/ake` symlink to it, both globally and in the project. This is not a symlink to the source checkout. Modes and fallback behavior may vary, especially on Windows; `--copy` requests independent copies. The [Skills agent table](https://github.com/vercel-labs/skills/blob/main/docs/agents.md) identifies Codex and Claude Code paths, not DSH as a target. DSH's filesystem provider can scan `.agents/skills` at project/user scope when enabled and configured accordingly; `DSH_AGENTS_HOME` and custom roots can differ. Installation alone does not prove an Agent loaded the Skill. Real Claude Code, Codex and Windows loading were not tested.

### Updates and migration

**Before running third-party install or update**, inspect and back up existing `ake` and `knowledge-ops` files, including project `.agents/skills/`, `.claude/skills/`, user `~/.agents/skills/`, `~/.claude/skills/`, flat `knowledge-ops.md`, and any configured DSH roots. Back up outside scanned Skill roots. Skills CLI is a separate tool: in the isolated macOS test, repeating `skills add` replaced a customized canonical `SKILL.md`; do not assume it preserves existing content or links. Manually merge your customizations and remove or move old entries only after reviewing them; otherwise differently named or project-level Skills may shadow or duplicate shared instructions. Neither `ake init` nor the migration hint modifies existing Skills.

`ake update [--dry-run] [--json] [--accept-customized]` is the deterministic CLI flow for updating the installed user-level Skill from the official GitHub repository. It shares one implementation with the Skill's `/ake update` entry; the Skill does not re-implement any of it.

1. **Preflight.** Checks the AKE host's Node.js >= 22.20.0 requirement, arguments, Git, installation identity, `HOME` and write permission. A lower runtime fails with `NODE_VERSION` before update work; legacy project-local CLI copies are neither installed nor upgraded. If an update is needed, the updater acquires and verifies the pinned Skills CLI as described below; `up_to_date` and `--dry-run` stop before that acquisition.
2. **Identity.** Resolves the loaded entry, the canonical directory and every AKE link, plus the lock entry, scope, mode, bundled version and resource completeness. A project-level, copied, development, multi-copy or ambiguous installation is refused; AKE never guesses which copy is live.
3. **Remote.** Reads the default branch and the latest commit from the remote itself (`git ls-remote --symref`); the branch name is never hard-coded. Only the official repository URL declared in this repository's own configuration is accepted — mirrors, redirects and local paths are refused.
4. **Up-to-date short circuit.** When the installed commit is the verified remote commit and the tree, resources and layout all match, it reports `up_to_date` without creating a backup or installing anything.
5. **Customization check.** Compares the installed tree with the tree of the *recorded* commit, not with the new target, so version differences are not misread as local edits. Modified files, extra files or an unprovable old commit block the update unless the user explicitly passes `--accept-customized`; the user initiating an update is not consent to overwrite customizations.
6. **Backup.** Copies the full canonical tree, the AKE links and the original lock bytes (including the "did not exist" state) to `<agentsHome>/ake/backups/<UTC-time-id>/` with a `manifest.json` and per-entry SHA-256. The copy is re-hashed before any replacement; an incomplete backup aborts the update. The backup lives outside every scanned Skill root.
7. **Install.** Runs the verified, isolated `skills@1.8.1` CLI as `skills add <repo>@<full-40-char-sha> --skill ake -g -y -a <already existing agent set>` with an argument array (no shell). It does not use `skills update`, which does not advance a commit-pinned installation, and it never writes the lock itself.
8. **Verify.** Compares the installed tree with the target commit's tree (content, modes, extra files, symlinks), checks the lock's `ref`, `skillPath` and other skill entries, confirms resources are complete and the load path/link layout is unchanged.
9. **Failure and manual recovery.** Once the installer may have started, any failure or uncertain result leaves the live state and backup untouched by automatic recovery. Keep all other writers stopped; record the reported backup path, inspect its `manifest.json`, `data/canonical` and `data/lock.json`, and inspect the current canonical tree, agent links and lock. Save a separate copy of the current state first. Only after reviewing differences and checking backup integrity should an operator manually restore the intended files, links and lock, without overwriting unrelated changes. Do not blindly retry. No automatic rollback or backup cleanup occurs on failure.
10. **Retention.** Only after a verified success, old AKE backups are pruned: keep the newest 3 valid AKE backups **and** everything younger than 30 days; delete only directories with a complete AKE manifest, never follow symlinks, never leave the backup root, and never delete user-created copies.

**Supported links.** The updater supports the canonical installation alone, canonical plus Claude Code, and canonical plus both Claude Code and CodeBuddy links. It does not claim general multi-Agent support: CodeBuddy-only links, copies, broken links and unknown layouts are refused. A previously installed older bundle does not gain this behavior until separately updated.

For the enumerated potential Skills CLI 1.8.1 path overrides (identified by static inspection, not individually verified against the real CLI), update and dry-run conservatively refuse before identity or network work if any of `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `VIBE_HOME`, `HERMES_HOME`, `AUTOHAND_HOME`, `GROK_HOME`, `SARVAM_HOME`, `REASONIX_HOME`, `FLATPAK_XDG_CONFIG_HOME` or `XDG_CONFIG_HOME` is nonempty, even when it looks like a default path; the report names variables, not values. An empty string does not trigger this check; whitespace-only values are nonempty and are refused. This is a fail-closed limitation for the enumerated variables, not a claim that every possible agent override has been identified. Isolated tests exercise AKE's refusal with synthetic override values, not each variable's behavior in the actual Skills CLI.

Two implementation details matter when reading the report. **Skills CLI acquisition:** only a real update that passes preflight obtains the fixed official `skills@1.8.1` package from `https://registry.npmjs.org` in an isolated temporary workspace, with lifecycle scripts disabled and package identity/version/entry/reported version checked. It does not use a `skills` binary from `PATH`, `npx --no-install`, or the user's npm cache. `up_to_date` and `--dry-run` do not invoke npm or acquire the CLI; acquisition failure stops before backup or installation. **Customization baseline:** for a local-source installation with no recorded commit, the recorded source directory is used as the baseline only when it is an absolute real directory, a Git top-level with a clean `skills/ake`, and it matches the installed tree byte for byte; otherwise customization stays `unknown` and `--accept-customized` is required. Because the update installs exactly the remote target commit, updating to a commit whose bundle does not yet declare `repository.url` is allowed but warns that the next update needs a version containing that field — and such a commit also cannot deliver features that are not yet on the remote branch.

`ake status` keeps the existing knowledge statistics and adds an `installation` object (OS, load/canonical path, scope, mode, bundled version, lock source/type, commit, resource completeness, agent paths, warnings). Its installation probe performs no Git, network or Skills-CLI call and writes nothing; project-root resolution keeps its existing behaviour. Remote availability is reported by `ake update`, not by `status`; when a value cannot be proven it is `null`/"unknown", never "latest".

**Limits.** The operator must keep other programs from modifying AKE throughout the update and pause all AKE CLI work/scripts that use the shared Skill bundle until the update completes and is verified. Replacement is *not* atomic: the Skills CLI rewrites the installed directory in place; there is no atomic isolation between readers and the update, and backup and verification do not constitute a transaction. Failure requires manual inspection and recovery. Only a canonical user-level installation under `~/.agents/skills/ake` (real directory) plus symlinks pointing at it is updated automatically. `DSH_AGENTS_HOME` relocates AKE's management/backup directory, but the Skills CLI has only been verified to write `HOME/.agents`, so a custom install root is refused instead of guessed. The first update may be started from an official source checkout (origin matches, `skills/ake` unmodified) to migrate a local-source installation; the content still comes from the remote target commit and the lock is still written by the Skills CLI, not by AKE. Native Windows W1-W4 update acceptance was verified on Node.js v24.22.2; this does not establish Windows ACL correctness, real rollback after an actual install failure, crash recovery, or every path/locking/file-in-use behavior. See the [test report](docs/test-report.md) for exact coverage and remaining limits. After an update the files on disk are current, but content already injected into a running Session is not refreshed: call `/ake` in a new message, or start a new Session; a full DSH restart is not required.

The shared CLI reports its declared version without opening a project: `node <Skill base>/resources/ake-source/scripts/ake.mjs version --json`. Preflight reports the Skill bundle version, bundled shared CLI version, and project config version; there is no separately installed project CLI version. Legacy `.ake/tools` copies are not inspected, run, or auto-upgraded. Only the Skill bundle is updated, through the shared `ake update` workflow above. There is no per-project upgrade command or automatic project upgrade engine. Preflight executes the bundled shared CLI's `status --json` against the project config and verifies the canonical project path; this validates project selection, not every task command, and cannot rule out side effects of the CLI itself.

For a target project, use only the loaded Skill's initialization flow: if `.ake/config.json` is absent, run `<Skill base>/bootstrap.mjs --dir <absolute-target> --dry-run`, inspect the plan and stop on conflicts before applying with the same helper; if a regular config already exists, preserve it and run `<Skill base>/preflight.mjs --dir <absolute-target>` once. Do not run the AKE source-checkout CLI against a target project. Existing `.ake/tools/` content is ignored and remains untouched. Knowledge, config, candidates and the publish log remain project-specific.

After initialization, invoke the shared CLI shipped with the installed Skill and always select the intended project explicitly. For an already initialized project, run preflight first. Before an option-bearing read-only search, inspect this same CLI's help in the same cwd/env and confirm every requested flag and value form is declared; if help is unreadable or an option is undeclared, do not run the search or silently drop the option.

```bash
node /absolute/path/to/ake-skill/resources/ake-source/scripts/ake.mjs --help
node /absolute/path/to/ake-skill/resources/ake-source/scripts/ake.mjs search "connection pool timeout" --project /path/to/your/project
node /absolute/path/to/ake-skill/resources/ake-source/scripts/ake.mjs validate --project /path/to/your/project
git add .agents docs .ake && git commit -m "chore: install knowledge ops"
```

Commit the installed layout: knowledge and its audit trail are project files, reviewed like code.

## The workflow

1. **Retrieve visibly before you build.** Before the first AKE CLI call in the retrieval stage, tell the user briefly that you are searching AKE knowledge; coalesce consecutive calls into one notice. In Agent Teams, only Lead/owner notifies the user; members report to Lead. Turn the task into keywords (module, technology, symptom, operation), search all four kinds, show category labels, read only hits whose recorded `scope`/`verified` still apply, and report which knowledge you used. A miss means "not found", not "does not exist".
2. **Route by stage; continue without redundant pauses.** A task-before trigger performs retrieval/applicability judgment only; it does not start capture. A task-after trigger assesses whether durable knowledge is worth capturing. Explicit `/ake` follows the stage(s) requested; the automatic completion-phrase route alone requires substantive engineering work, a loaded Skill, and an explicit confirmation such as “tests passed” or “acceptance passed.” Ordinary Q&A does not automatically trigger that route. Within the applicable stage, proceed through its permitted steps without inserting extra “continue?” pauses; only actual reviewer response and user release authorization are real wait gates. Candidate deduplication/creation/review happens only if task-after assessment finds supported, reusable, not-already-covered knowledge. No value → report `AKE · 本次无新增知识`; potentially valuable but insufficient core evidence → do not create a candidate, and report “potential knowledge pending evidence,” the gap, and verification path. Completion confirmation is not publication authorization, and ordinary language cannot guarantee host-side Skill loading/triggering. Before a candidate action, tell the user which result qualifies. Search for an existing owner first; prefer updating it, and report pending candidate IDs/statuses.
3. **Check evidence and obtain an independent review.** Run `candidate check` and inspect structure, scope/evidence, links, target, duplicate hints and verification. Reviewer evidence levels concern relevant core claims: A = strong direct evidence such as source code/change, executed test logs, reproducible results, or before/after comparisons when relevant. B = relevant current-context evidence such as current runtime/system status, actual browser inspection, this Session Agent’s direct verification, user confirmation, or readable configuration/install scripts/system state. B need not be persisted and needs no ID or separate evidence artifact; session observations do not require independent locatable corroboration. C = core claim lacks basic relevant support, evidence mismatches the claim, or available evidence contradicts it. A/B can support; C on a core claim is BLOCK. Missing session IDs, event numbers, standalone evidence files or unrelated topics alone do not lower a level or block. Report outcomes as PASS / PASS WITH LIMITATIONS / BLOCK, mapping to existing CLI verdicts `approve|request-changes|reject`: PASS → approve; PASS WITH LIMITATIONS → approve only when limitations are already explicit in the candidate, otherwise request-changes; BLOCK → request-changes if fixable, reject otherwise. Wait for the independent reviewer’s actual response; dispatch/acceptance or silence is not review. If no independent reviewer is available (including Single Session), say so and pause; author self-review may record the author’s own check but does not substitute for this workflow’s independent review. After request-changes, permit at most one automatic revision and one independent re-review; then pause if unresolved.
4. **Wait for explicit user authorization before publishing.** After a passing review, summarize the candidate and its limitations and wait for the user to authorize publication. Do not call `approve` or `publish` before that authorization. Then use `approve <id> --by <human> --confirm` and `publish <id>`; `--by` is a declaration, not a verified identity. Existing CLI automatic authorization remains available for compatibility but is not the Skill workflow default.

Candidate lifecycle (`draft → submitted → reviewed → approved → published`, with `rejected`/`superseded` branches) and the publish gate are specified in [docs/architecture.md](docs/architecture.md) §6.

### Single session

The Skill workflow does not substitute self-review for an independent review. If no eligible independent reviewer can be used, stop after preparing/checking the candidate and report that review is unavailable; do not authorize or publish. Once an independent reviewer has actually returned a passing result, continue only after explicit user authorization:

```bash
AKE_CLI="/absolute/path/to/ake-skill/resources/ake-source/scripts/ake.mjs"
PROJECT="/absolute/path/to/project"
node "$AKE_CLI" candidate new --kind note \
  --title "…" --target .agents/notes/proposed/process/2026-11-10-….md \
  --author "<agent>" --body /tmp/draft.md --project "$PROJECT"
node "$AKE_CLI" candidate submit C-0001 --project "$PROJECT"
node "$AKE_CLI" candidate check C-0001 --project "$PROJECT"
# Run only after the actual independent review result is received:
node "$AKE_CLI" review C-0001 --reviewer "<actual-reviewer>" --verdict approve --notes "checked scope, evidence, format, links, target, alternatives and verification" --project "$PROJECT"
# Run only after the user explicitly authorizes publication:
node "$AKE_CLI" approve C-0001 --by "<human>" --confirm --project "$PROJECT"
node "$AKE_CLI" publish C-0001 --project "$PROJECT"
```

### Agent Teams

The agent that did the task searches and proposes; an eligible member who did not generate the candidate reviews it. The owner waits for the reviewer's actual response (not dispatch acceptance or silence), summarizes the result and any limitations, then waits for explicit user authorization before using the declared human authorization mode and publishing. If no suitable reviewer exists, pause; an author self-review is not a substitute in this Skill workflow. Independent review is a declared-role check, not verified identity — see the limitations.

## Knowledge kinds

| Kind | Directory | Records | Machine layer |
|---|---|---|---|
| Agent Note | `.agents/notes/{proposed,implemented,rejected}/{class}/` | decisions and proposals, with rejected alternatives | official three-line header and path-encoded lifecycle |
| Defensive pattern | `docs/defensive-patterns/` | review rules and defect classes they prevent | `ake:` frontmatter + `**Prevents:**/**Reviewer check:**/**Boundary:**` labels |
| Post-mortem | `docs/postmortem/` | incidents, root causes, guardrails | header + required sections |
| Cookbook | `docs/cookbook/` | verified, repeatable procedures | `ake:` frontmatter + required sections |

One fact has one authoritative home; related knowledge is linked with relative Markdown links; `README.md` files inside the knowledge roots are index pages and are skipped by validation and search. The exact rules are frozen in [docs/architecture.md](docs/architecture.md) §4.

## CLI

| Command | Purpose |
|---|---|
| `ake init [--dir DIR] [--dry-run] [--merge-agents]` | underlying initializer invoked through the Skill bootstrap; do not run an AKE source-checkout CLI against a target project |
| `ake search <terms…> [--type TYPE] [--status STATUS] [--limit N] [--budget-bytes N] [--include-candidates] [--json] [--project DIR]` | keyword retrieval with coverage reporting |
| `ake validate [--project DIR] [--path FILE] [--json]` | format, link, id and lifecycle checks |
| `ake candidate new/submit/revise/list/show/check <id> [--project DIR]` | candidate lifecycle and drift/similarity report |
| `ake review <id> --reviewer NAME --verdict VERDICT [--notes TEXT] [--project DIR]` or `--self-review` | independent review or explicitly identified author self-review, bound to current content |
| `ake approve <id> --confirm [--project DIR]` or `--automatic --confirm` | CLI local automatic authorization mode (retained for compatibility; not the AKE Skill workflow default) |
| `ake approve <id> --by HUMAN --confirm [--project DIR]` | declared human authorization after explicit user authorization; identity is not verified |
| `ake publish <id> [--dry-run\|--reconcile] [--project DIR]` | fail-closed publication, atomic write, audit log line; `--reconcile` completes the ledger after an unknown result when the target already matches the approved content |
| `ake status [--json] [--project DIR]` | existing knowledge statistics plus installation information; installation probe is read-only with no Git, network or Skills-CLI call |
| `ake update [--dry-run] [--json] [--accept-customized]` | deterministic update flow for the installed Skill from the official GitHub source; `--dry-run` reports without writing; `--accept-customized` is required before overwriting detected local customizations; replacement is non-atomic and failure requires manual recovery |

This is the CLI command surface, not an alternate project-install route. For a target project, use the loaded Skill's `bootstrap.mjs` when `.ake/config.json` is absent and `preflight.mjs` when it is already initialized; then use the Skill-bundled shared CLI with `--project <absolute-target>`. Do not run the AKE source-checkout CLI against a target. Before an option-bearing read-only `search`, inspect that CLI's help in the same cwd/env and confirm every requested flag and value form is declared; if unavailable or undeclared, stop rather than dropping options or guessing.

Exit codes: `0` success, `1` validation/gate refusal (with the concrete reason), `2` usage error.

## Limitations

- **Not a security boundary.** In a shared writable workspace, ordinary file and shell tools can still edit formal knowledge directly, and `--by`/`--reviewer` strings are declarations, not verified identities. The publish gate checks only operations that go through the CLI; it does not prevent bypass, and there is no filesystem lock or multi-file transaction. Never report the workflow as mandatory enforcement.
- **Retrieval is lexical.** `ake search` matches tokens deterministically and reports its scope and coverage; it does not perform semantic retrieval, cannot guarantee recall, and does not decide whether knowledge still applies. Scores are ranking hints, not relevance probabilities. `--status` is an exact optional filter using each kind's status authority; missing status is `unknown`. `--budget-bytes N` defaults to unlimited and bounds only serialized hit payload bytes (UTF-8, excluding array brackets, top-level metadata/coverage diagnostics, and CLI framing). A budget-truncated search keeps valid structure and reports incomplete coverage; this is not a stdout hard limit. Before running an option-bearing search through the shared Skill CLI, the Skill checks that CLI's `--help` in the same cwd/env for each requested option and its value form. If any option is missing or cannot be confirmed, it does not run the search, drop flags, or retry; it reports the capability as unverified. A help declaration is not proof of runtime behavior; run a supported search once and preserve its raw coverage, and verify returned filters when `--type`/`--status` was requested.
- **The CLI retains a local automatic mode, but the Skill workflow requires user authorization.** AKE's Skill does not treat reviewer approval as publication authorization and does not invoke automatic authorization by default. It waits for explicit user authorization before the declared human mode and publication. The CLI's `--confirm` writes the selected authorization mode; `--by` remains an unverified declaration. Existing automatic mode remains available for compatibility but is not a security control or the documented Skill workflow.
- **Verification scope.** Unit tests and isolation-project integration tests run in CI-like conditions. Real DSH Single-Session and Agent Teams runs are recorded as individual observations, not statistics; retrieval recall, adherence and identity verification remain unverified. See [docs/test-report.md](docs/test-report.md).
- **Not implemented in v0.1**: DSH runtime plugin, MCP server, vector index, background service, web UI, central approval service, bilingual note triplets, the official `archived/` tree.

## Repository layout

```text
AGENTS.md            standing rules for developing AKE itself
src/lib/*.mjs        reusable logic: parsing, validation, search, candidate lifecycle, publish, init
scripts/ake.mjs      CLI entry
skills/ake/SKILL.md
templates/project/   what `ake init` installs
tests/               unit + isolation-project integration tests, fixtures
docs/                architecture, test report, design review, reviews
research/knowledge-ops/   research reports and official format references (evidence)
```

Developing AKE: `npm test`, `npm run check` (tests plus validation of this repository's own knowledge). Run `node scripts/benchmark-search.mjs` to generate a deterministic synthetic 100/500/1000-document retrieval benchmark (21 hot calls and 21 fresh-process runs per query); cold means a new Node process, not cleared OS caches. It reports median/p95 search latency, readFile calls (including config), compact serialized result-object bytes, asserted gold retrieval/filter expectations, and post-search RSS (not peak RSS). The deliberately repeated synthetic topics test lexical handling and do not represent real knowledge distributions or semantic recall. To compare a saved report, write the earlier JSON under ignored `.ake-tmp/` and run `node scripts/benchmark-search.mjs --compare .ake-tmp/search-before.json`; comparison includes latency, reads, result bytes, and RSS when corpus/query/options match. It uses only generated synthetic Markdown and does not measure real knowledge corpora or semantic retrieval.
